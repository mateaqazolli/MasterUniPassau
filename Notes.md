# NOTES — Restructuring Plan for the Reproduction Package

These notes summarise the professor's and reviewer's feedback and propose a concrete
target architecture for the repository. Nothing written so far needs to be deleted —
the existing material is good, it just needs to be **reorganised** and **automated**.

---

## 1. What the feedback actually asks for

Reading both emails together, there are exactly four requirements:

1. **README = reproduction blueprint, not a manual.**
   The current README documents every script. It should instead answer three
   questions per experiment: *Which experiment from the thesis is this? Which
   figure/table does it produce? Which single command reproduces it?*
   The current long-form content is valuable — move it to `docs/USAGE.md`
   (usage/developer guide) instead of deleting it.

2. **One "push-button" entry point.**
   A single script (`reproduce_all.sh`) that: builds the Docker environment →
   prepares all datasets → runs every experiment with the exact configurations
   used in the thesis (no interactive menus) → produces the tables and figures →
   exposes them on the host in `results/`.

3. **Self-contained Docker image.**
   The reviewer's specific complaint: `docker-compose.yml` currently bind-mounts
   the whole repo (`.:/workspace`) into the container. That means the container
   *depends on* and *can be affected by* the host's files while experiments run.
   Fix: `COPY` the sources into the image at build time; mount **only** a results
   directory back out. Code goes in at build time, only results come out at run time.

4. **Snapshot of the original thesis results.**
   Because SA/SQA are stochastic, re-runs produce *similar*, not *identical*,
   numbers. The repo must therefore contain a frozen copy of the exact tables and
   figures reported in the thesis (`original_results/`) so a reviewer can compare
   their fresh run against them.

Key principles (straight from the second email):

- **One script = one experiment (or one set of results).** Never a menu.
- **Clearly defined configurations.** All thesis parameters (trials, reads, dataset
  sizes, DB names) live in `config/*.env`, not typed interactively and not
  hard-coded in five different Python files.
- **No experiment overwrites another.** Every experiment writes into its own
  subfolder of `results/`.

## 3. Docker fix (the reviewer's main technical point)

### 3.1 Dockerfile — bake the sources in

Add after the pip install step:

```dockerfile
# Copy the project sources into the image so it is self-contained
COPY . /workspace
```

(Keep `.dockerignore` tight: exclude `.git`, `imdb_data/`, `results/`,
`original_results/` is fine to include, datasets that are generated should be
excluded.) After this change, the image is a sealed snapshot of the committed
code — editing files on the host has no effect on a running experiment.

### 3.2 docker-compose.yml — mount results only

Replace:

```yaml
    volumes:
      - .:/workspace          # ← remove: exposes sources to host modification
```

with:

```yaml
    volumes:
      - ./results:/workspace/results   # ← only the outputs leave the container
```

Everything else (postgres service, healthcheck, pgweb) can stay as it is.
The inner run scripts must then write/copy their final artefacts into
`/workspace/results/<experiment>/`, which makes them appear on the host
automatically.

> Consequence to remember: after any code change, `docker compose build` is
> required again, because the container no longer sees live host files. That is
> exactly the behaviour the reviewer wants.

## 4. The "building block" script design

Two layers:

**Layer 1 — host side, the button:** `reproduce_all.sh`

```bash
#!/usr/bin/env bash
set -euo pipefail
docker compose up -d --build                      # build image, start postgres
docker compose exec -T app bash scripts/prepare_datasets.sh
docker compose exec -T app bash scripts/run_wetgrass.sh
docker compose exec -T app bash scripts/run_nhanes.sh
docker compose exec -T app bash scripts/run_market_basket.sh
# Movie Link is optional (multi-GB IMDB download); enable explicitly:
[ "${RUN_MOVIE_LINK:-0}" = "1" ] && docker compose exec -T app bash scripts/run_movie_link.sh
docker compose exec -T app bash scripts/run_random_control.sh
docker compose exec -T app bash scripts/make_figures.sh
docker compose exec -T app bash scripts/make_report.sh   # optional HTML report
echo "Done. See ./results/ and open ./results/index.html"
```

**Layer 2 — container side, one block per experiment.** Each `run_<dataset>.sh`:

1. sources its `config/<dataset>.env` (thesis parameters, frozen);
2. runs the AnnealBN-CE pipeline for **SA**, then **SQA**, non-interactively;
3. runs the Chow–Liu + PostgreSQL benchmark for the same dataset;
4. runs the q-error calculation;
5. copies its final CSVs and PNGs into `results/<dataset>/`.

**Important implementation note:** the existing `dispatch.sh`,
`cardinality_benchmarks.sh`, `merge_results.sh` and `qerror_calculation.sh` are
*interactive* (they `read` answers from the keyboard). For the reproduction
scripts, either:

- (preferred) call the underlying Python modules directly with explicit
  arguments/environment variables, i.e. refactor the interactive shell scripts so
  the interactive menu is a thin wrapper around a non-interactive core; or
- (quick fix) pipe pre-recorded answers in (`printf '1\n2\n...' | bash dispatch.sh`)
  — works, but fragile if menu order changes, so treat it only as a stopgap.

The interactive scripts can stay in the repo for exploratory use — they just must
not be on the reproduction path.

## 7. The HTML report idea (optional, high impact, low effort)

Instead of adopting a workflow UI (Airflow/Prefect etc. — overkill here, and it
would make reproduction *harder* for the reviewer), have the last step generate a
single static page:

- `scripts/make_report.sh` runs a tiny Python script that walks `results/` and
  `original_results/` and writes **`results/index.html`**: for each experiment,
  the reproduced figure next to the original thesis figure, plus a small table of
  q-error summary statistics (median / max, reproduced vs. thesis) so "similar
  enough" is visible at a glance.
- No server, no dependencies beyond what's already installed — the reviewer just
  opens the file in a browser.
- pgweb (already in docker-compose, port 8081) remains the UI for inspecting the
  database; that's sufficient tooling.

This directly answers the professor's gold-standard phrasing: *push one button →
experiments run → charts are generated* — and the comparison with the thesis is
part of the generated output.

## 9. Small gotchas to watch

- `results/` must exist before `docker compose up` (compose creates it as root
  otherwise on Linux); add a `.gitkeep` and create it in `reproduce_all.sh`.
- Port 5432 conflicts on the host: consider mapping to `55432:5432` or removing
  the host port mapping entirely (nothing on the host needs it once everything
  runs inside the container network).
- NHANES auto-import only runs on a *fresh* postgres volume — `reproduce_all.sh`
  should either start from `docker compose down -v` or call the re-import script
  unconditionally.
- Movie Link: keep it opt-in (`RUN_MOVIE_LINK=1 ./reproduce_all.sh`) and say so in
  the README, since it needs a large external download.
- Timestamped output folder names are fine, but each `run_*.sh` should also copy
  (or symlink) its final artefacts to stable names in `results/<dataset>/` so the
  README can reference exact paths.
